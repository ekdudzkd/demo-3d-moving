## Problem Statement
사용자(일반 성인)가 이미지 1장을 올리고 그 이미지가 물체를 어느 쪽에서 본 것인지(정면/뒤/좌/우) 지정한다. AI가 보이지 않는 면을 추정해 3D를 만든다. 사용자는 6방향(앞·뒤·좌·우·위·아래) 정사영 패널로 결과를 확인하고, 패널 하나를 고른 뒤 "여기서 보면 옆으로 누워 있어, 세워줘", "더 두껍게"처럼 텍스트로 지시한다. LLM 대화처럼 지시를 반복하며 고친다.

지금은 생성 결과가 옆으로 눕거나 두께·비율이 맞지 않아도 고칠 방법이 없다. TripoSR은 seed를 바꿔도 같은 결과를 내므로 "다시 생성"으로는 해결되지 않는다.

## What Makes This Cool
- 6방향을 한 화면에 펼쳐 보면, 모델이 추정한 뒷면·옆면이 어디서 틀렸는지 바로 보인다. "그럴듯한 3D"가 아니라 "확인 가능한 3D"가 된다.
- 말 한 줄이 정확한 행렬 하나로 바뀌고, 수정할 때마다 검사·충돌체·GLB가 다시 만들어진다. "생성 성공 ≠ 사용 가능" 원칙이 편집에도 적용된다.
- 버전 타임라인에서 언제든 되돌릴 수 있고, 원본은 절대 변하지 않는다.

## Constraints
- 로컬 GPU는 RTX 4050 6GB. TRELLIS.2(약 16GB 필요)는 로컬에서 실행할 수 없다.
- CI와 테스트에서는 Mock만 사용한다(MockAdapter, Mock LLM). 대형 모델은 다운로드하지 않는다.
- 원본 메시와 보정 메시를 보존한다. mesh-ready-check에는 GPL 의존성을 넣지 않는다.
- 좌표 규약 D-022: y 위, 정면 +z, 이미지 오른쪽 +x.
- 작업 절차: IMPLEMENTATION_PLAN.md에 작업 ID를 만들고 상태를 갱신한다. 새 결정은 docs/decision-log.md에 기록한다.

## Premises (합의, 2차 의견 반영 후)
1. **방향 라벨은 "생성 후 회전 + 첫 편집 제안"이다.** "생성 조건"이 아니다. TripoSR은 어떤 입력이든 정면 카메라로 가정하고 생성한다(`triposr.py:207` `TO_Y_UP` 고정). 그래서 라벨은 생성 뒤 회전 행렬을 고르는 데만 쓴다. v1은 front/back/left/right를 정식 지원한다. top/bottom은 "실험 기능"으로 표시하고, 생성 직후 "높이 키우기"를 첫 편집으로 제안한다. (원래 전제 "라벨 = 정답"은 2차 의견에 따라 수정했다.)
2. **v1 편집은 전체 변환만 지원한다.** rotate(90° 배수만), 축별 scale, 균일 scale, mirror, stand_up. 바닥 맞춤은 사용자 op가 아니라 매 계산 뒤 자동으로 수행한다. **v0 = 보정 메시(repaired, 회전 없음)**. 버전은 `(v0 참조, op 리스트)`로 저장하고, op 리스트의 첫 항목은 항상 `label_rotation`(고정, 되돌리기 대상 아님)이다. 매번 v0에서 4×4 행렬 하나로 다시 계산해 정점에 반영한다. 원본(raw), v0, 모든 버전을 보존한다. 자세한 규약은 아래 "세부 규약"을 따른다.
3. **버전마다 repair는 다시 돌리지 않는다.** QC, 충돌체, GLB만 다시 만든다. `repair.py:121` `normalize_scale`이 크기 편집을 지우기 때문이다.
4. **"여기"는 사용자가 고른 패널이다.** 방향어(오른쪽·위·앞, 시계방향)는 그 패널의 화면 좌표로 해석한다. 화면 좌표를 월드 축으로 바꾸는 일은 결정적인 코드가 한다. v1에는 브러시가 없다.
5. **LLM은 스키마로 검증된 화면 기준 op JSON만 출력한다.** 메시를 다시 생성하지 않는다. 부위를 지정한 요청("귀를 길게")과 범위 밖 요청은 추측하지 않고 거절한 뒤 "전체에 적용할까요?"라고 되묻는다. undo와 revert는 LLM을 거치지 않는 버튼으로 둔다.
6. **형태 추가·제거, 재생성 편집, 부분 변형은 v1에서 제외한다.**

## Cross-Model Perspective (Claude 서브에이전트, 대화 맥락 없이 읽음)
- **가장 약한 전제**: "라벨이 정답, 생성 후 회전하면 된다"는 전제가 가장 약하다. TripoSR은 늘 정면을 가정하므로, top/bottom 입력은 회전해도 형상 자체가 틀린다(팬케이크 모양). **증명 방법**: 합성 물체 5개를 6방향으로 렌더 → 라벨별로 생성하고 회전 → 6방향 실루엣 IoU와 bbox 종횡비 오차를 비교한다. 4-4 비교표에 행만 추가하면 된다. 이 의견을 받아들여 전제 1을 수정했다.
- **기존 OSS(BlenderMCP, LLM Blender Agent)가 해주는 부분**: LLM → 도구 호출 → 결정적 엔진 구조. **직접 만들어야 하는 부분**: 패널 기준 방향어 해석, 범위 밖 요청을 거절하는 strict 스키마, 버전마다 QC·충돌체·GLB를 다시 만드는 게이트, Blender 없이 trimesh로 동작하는 구현.
- **권고**: LLM보다 먼저 "v0 + op 리스트 → 행렬 하나"인 버전 모델과 "패널 → 월드 축 변환 표"를 테스트와 함께 만든다.

## Approaches Considered
### Approach A: pages 데모만 (최소)
pages/app.js에 6패널 ortho 뷰, 정규식 Mock LLM, JS 행렬 변환만 추가. Effort S, Risk Low. 백엔드 파이프라인과 버전 보존·QC 게이트가 없어 프로젝트 원칙과 맞지 않는다. 데모에 보여주기용으로만 쓸 수 있다.
### Approach B: 백엔드 편집 모듈 + 버전 모델 + 프론트 패널 (선택)
`backend/app/edit/`에 op 스키마, 패널 기준표, 행렬 합성, 버전 저장, 버전별 QC·충돌체·export를 둔다. LLM은 adapter(Mock / 실제)로 연결한다. 프론트엔드 3D 뷰어 화면에 6패널 + 채팅 입력 + 버전 타임라인을 추가한다. pages 데모에는 같은 기준표를 JS로 옮긴다. Effort M, Risk Low~Med.
### Approach C: 실루엣 덧그리기 (재미있는 대안)
LLM 없이, 측면 패널 위에 원하는 윤곽을 그리면 bbox 비율로 축별 scale을 계산한다. 결정적이고 "그림으로 세계를" 콘셉트와 맞는다. 다만 회전이나 방향 보정은 표현하기 어렵다. v2 후보.

## Recommended Approach
**B.** 기존 파이프라인의 원칙(adapter 경유, Mock CI, 원본 보존, 버전마다 QC)을 그대로 지키면서, 2차 의견의 Critical 3건(E1~E3)을 구조적으로 해결한다. 구현 순서는 LLM 없이 결정적인 코어부터.

핵심 구조:
```
업로드(+view_label) → 기존 파이프라인 → v0 = 보정 메시(보존) → e0 = v0 × [label_rotation] (+자동 바닥 맞춤)
사용자: 패널 선택 + 텍스트 ─▶ EditPlanner(adapter: Mock|LLM) ─▶ PlanResult(ops | refuse | clarify)
          ─▶ ScreenOp[] 스키마 검증 ─▶ PANEL_BASIS로 WorldOp[] ─▶ 누적 범위 검사(E11)
          ─▶ compose(v0, [label_rotation, ...전체 op]) = 4×4 ─▶ 정점 반영 + 법선 재계산 + 자동 바닥 맞춤
          ─▶ QC + 충돌체 + GLB ─▶ edits/e{n}.json + e{n}.glb ─▶ 통과 시 active_version 갱신
```

## 세부 규약 (v1)
결정 기록: D-026(라벨 회전표·패널 기준표·피벗), D-027(버전 모델·활성 버전).

**버전 이름과 기준.** v0 = 보정 메시(파일 그대로 보존). e0 = `[label_rotation]`만 적용한 기본 버전. e{n} = e0의 op + 사용자 op. "처음으로 되돌리기"의 목적지는 e0이다. 실루엣 IoU 기준은 e0을 라벨 뷰 패널로 렌더한 것이다.

**피벗과 바닥 맞춤.** 회전, scale, mirror는 모두 현재 합성 메시의 bbox 중심을 피벗으로 한다. 계산이 끝날 때마다 bbox 중심의 xz를 원점으로, 최저점 y를 0으로 자동으로 맞춘다. 그래서 결과의 선형 부분은 피벗과 무관하다. 테스트에서는 정규화된 위치까지 비교한다. 바닥 맞춤은 사용자 op에서 뺀다.

**회전.** 90° 배수(k ∈ {±1, ±2, ±3})만 허용한다. "45도"처럼 다른 각도는 `refuse`(사유 `angle_not_supported`)로 처리한다.

**stand_up("세워줘") 규칙.** 결정적인 코드로 처리한다. LLM은 `stand_up`만 출력한다.
1. 가장 긴 bbox 축이 이미 y이면 no-op으로 판정하고 "이미 서 있어요"라고 응답한다.
2. 그렇지 않으면 그 축을 y로 보내는 90° 회전 후보 2개(+90, -90)를 만든다. 회전축은 가장 긴 축과 y에 모두 수직인 월드 축이다.
3. 두 후보 중 부피 중심(volume centroid)이 bbox 중심보다 더 낮은 쪽을 고른다(무거운 쪽이 아래). 차이가 bbox 높이의 2% 미만이면 +90을 고르고, "거꾸로면 '뒤집어줘'라고 하세요"라는 안내를 붙인다.
4. 테스트: 옆으로 눕힌 원뿔 → 밑면이 아래로 선다. 대칭인 막대 → +90을 고르고 안내가 붙는다.

**EditPlanner 인터페이스.**
- 입력: `{text, panel ∈ {front,back,left,right,top,bottom}, history: 최근 사용자 op 5개, extents_world, cumulative_scale}`.
- 출력 `PlanResult`(셋 중 하나):
  - `{kind:"ops", ops: ScreenOp[1..4]}`
  - `{kind:"refuse", reason_code: part_edit|out_of_scope|angle_not_supported|out_of_range|unparseable, message}`
  - `{kind:"clarify", question, suggested_text?}`
- 실제 LLM 응답이 스키마를 위반하면 1회 재시도한다. 그래도 실패하면 `refuse/unparseable`로 처리한다. MockPlanner와 실제 adapter는 같은 계약 테스트를 공유한다.
- v1에서 플래너로 보내는 데이터는 텍스트, 패널 id, 숫자뿐이다. 이미지는 보내지 않는다.

**ScreenOp 스키마.** 모든 op는 `target:"whole"` 고정이다.

| type | 필드 |
|---|---|
| `rotate90` | `axis: screen_right\|screen_up\|toward_viewer`, `k: ±1..±3` |
| `scale_axis` | `axis`(위와 같음), `factor: 0.1..10` |
| `scale_uniform` | `factor: 0.1..10` |
| `mirror` | `axis` |
| `stand_up` | 필드 없음 |
| `invert_last` | 필드 없음. 직전 사용자 op의 역연산을 결정적으로 계산("반대로") |

"아까처럼"은 `clarify`로 처리한다. 형용사 기본 배율은 "두껍게/길게/크게" ×1.25, "많이" ×1.5, 반대말은 그 역수다.

**버전 이력.** append-only 선형 이력이다. undo와 revert는 "목적지 버전의 op 리스트를 복사한 새 버전"을 추가한다. 이력은 잘리지 않는다.

각 버전은 `prev_state`(이 버전 직전에 활성이던 상태의 버전)를 저장한다. 규칙:
- **편집**: 새 버전 N의 `prev_state` = 편집 시점의 활성 버전.
- **undo**: 활성 A에서 undo하면 T = A.prev_state의 op 리스트를 복사한 새 버전 U를 만들고, U.prev_state = T.prev_state로 둔다. 연속 undo는 체인을 따라 내려가며 e0에서 멈춘다. e0은 prev_state가 없어서 undo 버튼이 비활성화된다.
  - 예: e1(prev e0), e2(prev e1) → undo → e3 = e1의 op, prev e0 → undo → e4 = e0의 op → 더 이상 undo 불가.
  - failed 버전은 활성이 되지 않으므로 체인에 들어가지 않는다.
- **revert**: 새 버전 R = 목적지 op 복사, R.prev_state = 활성 버전.
- undo 목적지는 서버가 계산한다.
- 테스트: e2에서 undo를 2번 하면 e0과 같은 op 리스트가 된다.

**API.** 계획(plan)은 동기, 적용은 비동기다.
- `POST /api/assets/{id}/edits {panel, text}`: 플래너를 동기로 실행한다.
  - 200 `{kind: refuse|clarify, message}`: 새 버전 없음
  - 202 `{kind: ops, job_id, version, ops}`: 적용 작업을 큐에 넣음
  - 409: 같은 asset에 진행 중인 편집 작업이 있음
- `POST /api/assets/{id}/edits/undo` → 202 `{job_id, version}`. e0이면 409 `nothing_to_undo`.
- `POST /api/assets/{id}/edits/revert {to_version}` → 202 `{job_id, version}`
- `GET /api/assets/{id}/edits` → 버전 목록(`status: pending|ready|failed`, `ops`, `intent`, `prev_state`)과 `active_version`

적용(행렬 → QC → 충돌체 → GLB)은 기존 작업 큐와 워커(D-002)로 처리한다. 완료는 기존 작업 SSE로 `edit_ready`/`edit_failed`를 보내고, 성공하면 `active_version_changed`를 보낸다. asset마다 한 번에 하나만 실행한다. edit, undo, revert 중 어느 작업이든 asset에 pending 상태로 있으면, 세 엔드포인트 모두 409 `edit_in_progress`를 돌려준다. 그래서 asset마다 pending 버전은 최대 1개이고, 목적지·prev_state·E11 검사가 항상 최신 활성 버전 기준으로 계산된다. 테스트: 편집이 pending일 때 undo를 요청하면 409.

**QC 실패 버전.** 실패 판정 기준은 두 가지다. mesh-ready-check의 ERROR 등급 문제, 또는 export·충돌체 생성 예외. 이때 버전 파일과 QC 보고서를 `status: failed`로 저장한다. 활성 버전은 그대로 유지하고, 월드로 export하지 않는다. 채팅에는 실패 유형(한글 이름)과 "되돌리기" 버튼을 띄운다. 다음 편집은 활성 버전을 기준으로 한다.

**E11 한계와 QC 기준의 관계.** E11은 extents의 최대/최소 비율을 20 이하로 제한한다. 그래서 최소/최대는 0.05 이상이고, mesh-ready-check `flat_ratio`(0.02, WARN)와 collider `FLAT_RATIO`(0.01, 상자로 전환)보다 항상 크다.
- 범위 안의 납작화는 실패하지 않는다.
- 범위 밖의 요청은 플래너 단계에서 `refuse/out_of_range`로 거절되고 버전도 생기지 않는다.

전체 변환은 위상을 바꾸지 않으므로, 실제 실패 경로는 qhull 예외 같은 export·충돌체 오류다. 이 경로는 기존 실패 주입(fail injection)으로 테스트한다. 편집 버전 QC는 `target_size=None`으로 실행한다. 그렇지 않으면 크기 편집마다 `wrong_scale` 경고가 뜬다(E15).

테스트:
- 실패 주입 → failed 버전이 생기고 active_version은 바뀌지 않는다.
- 비율 > 20 요청 → refuse, 버전 없음.

**활성 버전과 월드.** asset에 `active_version` 포인터를 둔다. `asset.json`의 `mesh_url`, `collider`, `collision_type`, `bounds`는 항상 활성 버전의 값이다. 월드는 처음 로드할 때와 SSE로 `active_version_changed` 이벤트를 받을 때 그 값을 다시 로드한다. MVP 월드에는 객체가 하나이므로, 배치된 인스턴스를 위치만 유지한 채 새 메시로 교체한다.

**패널 표시 범위.** asset마다 고정한다. e0 최대 extent의 1.5배이고 바닥선이 기준이다. 어떤 버전이 이 범위를 넘으면 범위를 1.1배 여유로 넓히고, 눈금자 라벨을 갱신한다. e0의 외곽선은 점선으로 겹쳐 그려서 크기 변화가 항상 보이게 한다.

**정점 속성.** 위치에 M을 곱한다. det<0이면 면 순서를 뒤집는다. 그다음 법선을 다시 계산한다(trimesh face/vertex normals 캐시 초기화). UV, 정점 색, 텍스처 이미지는 그대로 둔다. 테스트: 텍스처 메시를 mirror한 뒤 UV 배열이 같은지, `is_winding_consistent`인지, 부피가 0보다 큰지 확인한다. 축별 scale 뒤 법선 길이가 1인지 확인한다.
